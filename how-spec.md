# How — Working Document

## Per-element research and options

### Language(s) / stack
**Research (precedent: rich):** Real comparables split into three camps. (1) Hand-rolled web-native: Slow Roads — the product's named presentation benchmark — is vanilla Three.js plus a custom minimal physics engine, with a splash screen deferring scene init to protect time-to-fun (web.dev case study); TypeScript + Vite is the de facto toolchain, and performance-focused games mostly stay vanilla rather than adding react-three-fiber. (2) Integrated web-native engines: Babylon.js (most mature WebGPU backend with WebGL2 fallback, first-party PBR/ACES/GUI/audio/Inspector) and PlayCanvas ship commercial production workloads. (3) Editor exports: most portal 3D games are Unity WebGL builds, but an entire optimization discipline exists just to fight 20–100 MB payloads; Godot 4 web export is documented as worse (Compatibility renderer, SharedArrayBuffer issues). As of 2026 WebGPU ships by default in Chrome/Edge/Firefox(Windows/macOS)/Safari 26, so "WebGL2 baseline, WebGPU optional" is the current pragmatic posture, not a conservative one.
**Options:**
- **A —** Lean composed web-native stack per the guidance's own tech direction: TypeScript 5.x (strict) + vanilla Three.js (WebGLRenderer on WebGL2 as shipping baseline; WebGPURenderer as flag-overridable progressive enhancement) + Vite. No UI framework, no React: diegetic UI rendered in-scene (canvas-textured dot-matrix LED board, emissive panel materials); ESC sheet and splash as plain HTML/CSS overlays. Post via pmndrs `postprocessing` (ACES, bloom). All physics (fixed-timestep ballistics with drag+Magnus, signed-ε contact model, Verlet net cloth) as a dependency-free pure-TS module, unit-tested headlessly with Vitest. Web Audio API directly (no Howler). Mixamo/Blender → glTF/GLB with Draco/meshopt + KTX2/Basis. Versioned JSON in localStorage + file export/import. Ships as pure static files; ESLint + Prettier + tsc strict as toolchain gates. Smallest payload (~1–2 MB gz engine+code before assets) directly protects the ≤10 s / ≤60 s gates; total loop ownership suits event-timestamped frame-rate-independent input; pure-TS physics makes the must-be-correct math testable without a browser.
- **B —** Integrated web-native engine: TypeScript 5.x + Babylon.js 8 + Vite, first-party end to end — PBR + ACES via ImageProcessingConfiguration, DefaultRenderingPipeline bloom, native WebGPU engine with automatic WebGL2 fallback, built-in skeletal animation/retargeting for the Mixamo batter, Babylon GUI + DynamicTexture for boards, Audio Engine v2, Inspector profiling. Physics remains custom pure-TS (Havok plugin explicitly NOT used). Same glTF/KTX2 pipeline, Vitest, localStorage, static deployment. Cleanest realization of "WebGPU optional"; cost is ~3–5 MB extra runtime payload and loss of the hand-rolled showcase character.
- **C —** Editor-driven engine export (the dominant portal route): Unity 6 LTS (C#) Web build on URP, or Godot 4.4 web export on the Compatibility renderer. Buys Humanoid retargeting for the batter, built-in cloth, Timeline, audio mixer, profiler, visual lighting editor; gameplay physics still custom C#. Ship Brotli-compressed, code-stripped static files; PlayerPrefs/IndexedDB persistence + JSON export. Strongest tooling for the rigged batter, but documented 20–100 MB payloads, wasm warm-up, and lowest-fidelity web renderers directly threaten the locked ≤10 s load and 60 fps presentation gates.

### Deployment & access
**Research (precedent: rich):** Four documented patterns. (1) Hosted static web at a memorable URL — the premium-browser-3D norm and the named benchmark: slowroads.io is a static Three.js site, instantly playable, no signup. (2) The standard Vite pipeline behind it: `vite build` emits static `dist/`, deployed to GitHub Pages / Netlify / Cloudflare Pages or zipped for itch.io; relative base makes the artifact host-agnostic. (3) Portal distribution (Poki/CrazyGames) has the highest reach but contractually requires their ad/analytics SDKs — eliminated outright by the locked "local and private" fence. (4) Installable offline PWA (manifest + service-worker precache) launches from the dock and plays fully offline (MDN/Workbox, well documented). Hard constraint: ES-module builds do not run from file:// (CORS), so local play requires any tiny static server; single-file inlining is poor for an asset-heavy 3D game.
**Options:**
- **A —** Local-only, repo-as-distribution: canonical play path is `npm run build` + `npm run preview` (or `npx serve dist`) at a localhost URL; no public deployment, no hosting account, no CI; dist/ is relative-base, fully vendored, zip-portable to another machine. Strictest reading of fence 4; serves the build-for-yourself first user and the same-machine hot-seat persona fully — but the "one URL away" promise becomes owner-only.
- **B —** Self-contained static artifact + free static hosting at a stable public URL (the Slow Roads model): `vite build` (relative base, all fonts/models/audio/textures/decoder-WASM vendored, zero runtime network requests beyond same-origin asset load) published to GitHub Pages / Netlify / Cloudflare Pages by a minimal CI step; the identical artifact runs from any local static server and is zip-ready for itch.io. No backend, no accounts, no analytics. Spec notes per-origin saves (hosted vs localhost are separate careers; Export/Import bridges) and pins the cold-load ≤10 s budget with Draco/KTX2/audio compression and immutable content-hash caching. Literal fulfillment of the locked "one URL and one key away."
- **C —** Installable offline-first PWA layered on B: manifest + service worker (vite-plugin-pwa/Workbox) precaches the full asset set on first visit; thereafter instant loads, zero network ever, desktop/dock install in a standalone window; versioned SW updates with an in-game "NEW VERSION — RELOAD" prompt. Strengthens fence 4 into a mechanical guarantee and hardens warm loads — at the cost of service-worker cache-invalidation complexity and stale-version risk.

### Architecture
**Research (precedent: moderate):** Browser-3D game architectures cluster into three patterns. (1) Logic/render separation around a fixed-timestep accumulator — Gaffer on Games' "Fix Your Timestep" is canonical, and JS gamedev literature consistently advises a headless deterministic logic layer for testability. (2) ECS (ECSY, miniplex, bitECS) — the webgamedev.com-recommended pattern; payoff comes with many similar entities, cost is implicit execution flow. (3) Scene-graph/actor OO coordinated by statecharts (XState + Three.js is documented) — the de facto default in small Three.js projects. The premium benchmark, Slow Roads, used none of the general machinery: bespoke minimal physics, a pared-down single-purpose loop, work scheduled across frames. Web Worker physics offload is proven (surma.dev OMT case study) but high-frequency worker↔main messaging costs real performance and requires push-model transferable buffers.
**Options:**
- **A —** Deterministic headless sim core + presentation adapters (hexagonal, single-threaded). `core/` (zero Three.js/DOM imports) owns the entire rules-of-the-game: Visit + Pitch Cycle statecharts, machine cadence, analytic pitch schedule (release → plate-crossing per tier), signed-ε contact model + per-speed window tables, ballistic integrators (pitch: gravity+drag; post-contact: +Magnus; open-field projection simulated to ground), net-plane gameplay response, scoring/medals/progression, stats aggregation. Advances via a fixed-dt accumulator fed from a timestamped input-event queue; emits immutable per-tick snapshots + discrete domain events (FEED, RELEASE, SWING_JUDGED, CONTACT, NET_HIT, ROUND_END, UNLOCK). `presentation/` (Three.js scene, camera director, visual-only Verlet cloth, board/monitor canvas renderers, audio, batter animation) subscribes to events and renders alpha-interpolated snapshots. `platform/` adapters: input stamped at DOM event time via performance.now(), versioned localStorage save service, seedable RNG, clock, F3 diagnostics. One-way data flow; deterministic seedable core means timing tables, scoring, projection math, and all three locked acceptance parameterizations run as headless Vitest suites with scripted keypress timestamps.
- **B —** ECS world with a fixed-order system pipeline (miniplex-style): entities for live ball, settled balls, machine, net (cloth-node buffers as a component), batter, boards; plain-data components; logic systems in fixed order inside the fixed-dt tick (InputDrain → MachineCadence → PitchFlight → SwingJudgment → ContactImpulse → ClothStep → NetCollision → OpenFieldProjection → Scoring → Progression → StatsAggregation → SaveDirty); render-rate read-only systems sync to Three.js. Strict data/logic separation by construction and uniform handling of floor balls/cloth nodes; honest cost — data-oriented indirection oversized for one live ball plus a fixed cast.
- **C —** Diegetic stage-and-actors with central Director statecharts; numeric physics in a Web Worker. One self-contained actor module per station (PitchingMachine, Ball pool, Net, Batter, LEDBoard, StatsMonitor, ControlPanel, TokenSlot, BatRack, CameraDirector); Director runs the Visit/Pitch-Cycle statecharts and choreographs via typed commands + event bus; GameStore wraps the versioned save. Swing judgment stays main-thread and analytic (ε from DOM-event timestamp vs precomputed plate-crossing schedule); post-contact flight + Magnus, open-field projection, and Verlet cloth integrate at fixed dt in a Worker streaming transferable Float32Array buffers back. Maps 1:1 onto the locked diegetic-station UX and hard-isolates physics spikes from the 60 fps gate; price — gameplay logic distributed across actors is harder to test headless, and the worker message schema is a second serialization boundary.

### Code organization
**Research (precedent: moderate):** Three documented patterns, none universally standard. (1) Actor/Experience OOP — the community norm taught by Three.js Journey (singleton Experience; Utils/; World/ with one class per scene actor; sources.ts manifest), echoed by Discover three.js (components vs systems) and most open-source three.js games. (2) ECS folders (bitECS/miniplex): components/systems/archetypes, systems as pure functions, scheduling left to the app. (3) Layered sim/render separation around the Gaffer accumulator, with event-timestamped input feeding a fixed-step sim — cited payoffs are determinism, replay-from-inputs, identical behavior at any fps, headless testability. TS conventions stable across all three: src/ by feature, public assets separate, versioned config at root. Slow Roads is closed source; no published file tree exists for a premium single-scene browser sports game — structure must be synthesized.
**Options:**
- **A —** Layered structure with a deterministic pure-TS core; dependency rule enforced via ESLint import boundaries (core imports nothing outside core; scene/ui/audio import core types, never vice versa). Tree: `src/main.ts` (splash, WebAudio unlock, boots App); `app/` (App composition root, GameLoop — rAF + fixed-step accumulator + interpolation alpha, Quality presets + auto-detect, Diagnostics/F3, typed events bus); `core/` — PURE TS: pitchCycle.ts (locked ARMED→FEED→RELEASE→FLIGHT→INPUT→OUTCOME→RESOLUTION→BOARD_REVEAL machine), physics/{ballistics, projection, cloth, collision}, contact/{timingWindows, contactModel}, rules/{round, scoring, progression, stats}, constants (cage dims, tiers, physics consts), types, rng; `input/` (swing.ts — SPACE keydown @ performance.now(), debounce, lockout, TAKE; uiKeys.ts; pointer.ts raycast click parity); `scene/` — three.js only: CageScene, CameraRig (OTS + station moves), Lighting, PostFX (ACES, bloom), actors/{Batter, Machine, Ball + settled pool, Net cloth-mesh binding, BatRack, TokenSlot}; `ui/` (diegetic/{LedBoard + boardPages, MachinePanel, StatsMonitor}, overlay/{EscSheet, Splash, KeyHints, Toasts}); `audio/` (AudioEngine, cueMap event→sample); `persist/` (schema versioned, store + visibilitychange flush, migrate, exportImport, clipboard); `assets/` (manifest, loaders GLTF/KTX2/audio); `tests/` (Vitest over core/ only: ε tables, EV/LA mapping, projection checks, scoring/medal thresholds, state-machine transitions); `public/assets/`; index.html, vite.config.ts, tsconfig.json. Mirrors the spec's own How decomposition one-to-one.
- **B —** Experience/actor structure (Three.js Journey norm): one class per in-world thing owning its geometry, animation, behavior, and sounds; gameplay state on World; shared services in Utils; pure math importable from World/helpers/ but no hard sim/render boundary. Experience/{Experience, Camera, Renderer, PostFX, sources, Utils/{Time, Sizes, Resources, EventEmitter, Debug, Quality}, World/{World, Cage, Lighting, Turf, Machine, Batter, Ball, Net, LedBoard, StatsMonitor, TokenSlot, BatRack, Round, Scoring, Progression, Stats, helpers/}, Audio/, Save/}; overlay/, input/. Cohesion-by-object minimizes cross-file coordination for an automated build; cost — no enforced determinism boundary.
- **C —** Data-oriented mini-ECS with explicit fixed-step pipeline: ecs/{world, components, archetypes, resources (pitchCycle, round, inputQueue singletons)}; systems/pipeline.ts — one file making the per-pitch system order auditable; one file per system; data/ as pure config tables (tiers, timingWindows, scoringTables, medalThresholds, cage, physicsConstants); render/, ui/, audio/, save/. Systems-as-pure-functions give headless testability with explicit sequencing; uniform entity handling for settled balls + cloth nodes; oversized indirection for a fixed cast.

### Data model
**Research (precedent: rich):** Comparables converge on client-side single-blob persistence with manual export: Cookie Clicker keeps one serialized version-tagged blob in localStorage with Export/Import of the save string. Web-game save guidance is consistent: localStorage under ~1 MB (IndexedDB above); schema version embedded in every save + forward migration chain at load; save on visibilitychange AND beforeunload (unload writes must be synchronous → localStorage); default storage is best-effort evictable, so request navigator.storage.persist() and always offer file export. Domain entities follow HitTrax: per-swing records (EV, LA, distance, outcome), session summaries, trend charts, profiles, leaderboards — exactly the locked SwingRecord/Round/Session/PB/top-5 set. Size math: 10,000 swings ≈ 1.2–1.8 MB verbose JSON, ≈ 0.6 MB compact — at the localStorage comfort boundary, the one real tension.
**Options:**
- **A —** One denormalized JSON document, straight-through: single localStorage key `bc.save` holding the whole versioned tree exactly as the locked I/O describes (meta/settings/loadout/tiers map with medals + pbs + top5 + averages + clubs/sessions kept forever/swingLog FIFO-capped at 10,000/recentRounds). Materialized stats updated in one in-memory transaction at round end; whole document stringified at round end + visibilitychange/beforeunload only; export IS the document; import = parse → version check → linear migration; `bc.save.bak` previous-good copy. Smallest code surface; worst case ~1.5–2 MB fits the 5 MB quota.
- **B —** Same single versioned localStorage document, normalized, compact-encoded, crash-safe: SwingRecords as fixed-order tuples with integer enums and quantized numerics ([t, tierIdx, epsMs, gradeEnum, sprayEnum, evMphX10, laDeg, carryFt, points, batEnum]) cutting the 10,000-swing cap to ≲0.6 MB; RoundRecords reference swing-log index ranges; lifetime averages recomputed from the log/session aggregates rather than trusted blindly. Durability engineering: double-buffered verify-then-promote writes (serialize → `bc.save.next` → re-parse to verify → promote, retain `bc.save.bak`) so quota errors, mid-write tab kills, or corrupt blobs always fall back; navigator.storage.persist() at first save; runtime schema validation on import before the migration chain; newer-schema saves refused with a board message; pretty-printed export. Applies the marketplace's actual engineering guidance to protect the months-long PB career against eviction, corruption, and hostile imports.
- **C —** Event-sourced ledger with derived projections, still one versioned localStorage document: append-only events (SESSION_START, ROUND_START, SWING, ROUND_END, MEDAL_EARNED, TIER_UNLOCKED, HISCORE_ENTERED, LOADOUT_CHANGED); the swing cap implemented as compaction into immutable SessionAggregate snapshots (making "log capped, aggregates forever" true by construction); all UI stats are projections replayed at load and cached under derived{}. Single source of truth eliminates stat drift — the board can never claim a PB the log doesn't contain — and the ledger pre-builds deferred features (streak, replays); cost is projection/replay code, the most code for the same persisted facts.

### External dependencies / integrations
**Research (precedent: rich):** Two camps. Showcase camp: Slow Roads is Three.js + custom minimal physics with near-zero third-party runtime deps. Ecosystem camp: typical 2025–26 three.js games layer small curated libs — Rapier (Apache-2.0 WASM, -compat base64-embeds the wasm), three-mesh-bvh, pmndrs/postprocessing (the WebGL2 standard while three's TSL/RenderPipeline is the native WebGPU path). Audio: Howler is battle-proven but low-latency 3D SFX is commonly done via three's AudioListener/PositionalAudio over raw Web Audio; HTML5 audio unsuitable for timing-critical SFX. Asset pipeline strongly standardized: Mixamo (royalty-free embedded use; raw files not redistributable), @gltf-transform/cli with Meshopt (animated) + Draco (static) + KTX2/Basis (UASTC normals, ETC1S albedo), decoders self-hostable. Content sources: Poly Haven/ambientCG CC0, Kenney, Sonniss GDC packs, freesound-CC0, and the DSEG segment font family (OFL-1.1) purpose-made for LED typography. Persistence best practice matches the locked I/O (versioned save, persist(), export/import, visibilitychange + synchronous beforeunload). The locked "Local and private" fence eliminates the entire portal/analytics SDK category; all options converge on zero runtime services.
**Options:**
- **A —** Bespoke core, near-zero runtime dependencies (Slow Roads doctrine): exactly one runtime npm dependency — three (pinned minor), using bundled examples/jsm modules (GLTFLoader + DRACOLoader/KTX2Loader/meshopt decoder, AnimationMixer, AudioListener/PositionalAudio, EffectComposer bloom). Everything else first-party: fixed-timestep integrator (also run to ground for projection), Verlet cloth + cage collision, LED board as custom dot-matrix shader with DSEG font atlas, versioned save layer + persist(), mulberry32 RNG. Dev-time only: typescript, vite, vitest, eslint+prettier, @gltf-transform/cli; decoder WASM vendored same-origin. Content-time services never at runtime: Mixamo, Poly Haven/ambientCG, Sonniss/freesound-CC0. LICENSES.md inventory. No-network fence satisfied by construction, auditable via one dependency. Risk: hand-rolling bloom tuning and SDF-quality text costs polish time the presentation gates will spend elsewhere.
- **B —** Curated micro-dependency stack: A's core plus ~5 single-purpose MIT libs where first-party buys nothing — (1) postprocessing (pmndrs) for the production bloom/SMAA/tonemap chain on WebGL2 (three's native TSL pipeline on the optional WebGPU path); (2) three-mesh-bvh for ball-vs-net/frame proximity and raycast queries; (3) troika-three-text for SDF text on the dense stats monitor; (4) idb-keyval mirroring the save into IndexedDB beside the localStorage primary; (5) tweakpane (or bundled lil-gui) behind a dev-only flag for live-tuning timing windows, drag/Magnus coefficients, and scoring constants. Dev toolchain adds playwright (automating the three locked acceptance scenarios) and vite-plugin-glsl. Governance: lockfile pinning, no transitive network calls, ~2.5 MB gz JS budget, LICENSES.md, zero runtime services. Keeps the differentiating sim bespoke while not re-deriving solved problems.
- **C —** WASM physics engine owns the contact world: three + @dimforge/rapier3d-compat. Rapier owns the cage's physical aftermath (ball-vs-net/frame/floor, restitution, resting contacts of ten settled balls); everything scored stays first-party and deterministic (pitch flight, signed-ε model, post-contact drag+Magnus, projection) — the engine never touches a number on the LED board. Costs stated: ~1.5–2 MB bundle, a determinism boundary, version pinning. Babylon+Havok recorded as considered-and-rejected. Derisks resting contacts and net believability — the classic hand-rolled-solver failure modes — at real payload and boundary cost.

## Holistic combinations

### Combination 1 — 1A/2B/3A/4A/5B/6A
**"The Deterministic Showcase (purist)."** The guidance's own tech direction at its leanest, Slow-Roads-doctrine reading: vanilla TypeScript + Three.js + Vite with a single runtime dependency; one static artifact published to a free host at a stable public URL (and runnable identically from a local static server); a zero-DOM deterministic sim core under a fixed-tick accumulator with presentation subscribing to snapshots + events; folders that mirror the layers one-to-one; a hardened single-document localStorage save (compact tuple swing log, verify-then-promote double-buffered writes, persist(), validated imports). Every signature system — ballistics, contact model, projection, cloth, LED board — is first-party.
**Pros:** Smallest possible payload of any combination (~1.2–1.5 MB gz JS before assets) — the strongest guarantee on the locked ≤10 s cold-load / ≤60 s first-pitch gates. One-dependency supply chain makes fence 4 ("local and private") auditable by inspecting a single lockfile entry; zero runtime origins by construction. The deterministic, seedable core turns ε-window tables, EV/LA formulas, projection math, scoring/medal thresholds, and all three locked acceptance parameterizations into headless Vitest suites — the automated no-feedback pipeline can prove its own acceptance criteria without a GPU. Identity match with the marketplace positioning (same construction as the named benchmark, preserving the "this runs in a browser?" beat). 5B's save engineering protects the months-long PB career — the product's emotional core — against eviction, corruption, and bad imports.
**Cons:** The hand-rolled post chain is the weak joint: bloom quality and AA via three's examples EffectComposer is the slow multi-pass path, and writing a merged production chain by hand is specialist polish work — a cheap-looking bloom undermines the very presentation gate this combination exists to serve. No browser-level acceptance automation and no live tuning UI unless hand-built, yet the objective function explicitly demands playtest-tuned thresholds. Everything bespoke means every visual/audio edge case (cloth jitter, ball settle) is first-party with no battle-tested fallback.
**Objective alignment:** Maximal on time-to-fun and the privacy fences; the mastery loop is fully served (deterministic ε math, F3-observable input-to-judgment latency). Its one exposure is execution *quality* of the presentation gate — it trades a small, standard dependency for ideological purity, and the objective function does not reward purity.

### Combination 2 — 1A/2C/3A/4A/5B/6B
**"The Installed Training Facility (pragmatist-plus)."** The same deterministic spine — lean Three.js stack, hexagonal core, layered folders, hardened save — upgraded for permanence and production polish: an installable offline-first PWA (Workbox precache, dock icon, versioned update prompt); five curated micro-deps (pmndrs postprocessing, three-mesh-bvh, troika-three-text, idb-keyval IDB mirror, tweakpane dev tuning); Playwright automating the three locked acceptance scenarios in a real browser.
**Pros:** The production post chain and SDF text directly serve the 60 fps gate and the stats monitor's legibility — each dependency maps to a locked requirement. Offline install makes fence 4 mechanical (after first visit the game *cannot* touch the network) and warm loads near-instant; a dock icon suits the months-long career. tweakpane + Playwright operationalize exactly the tuning and acceptance loops the objective function demands. IDB mirror + persist() + double-buffering is the strongest save-durability story of the three.
**Cons:** The service worker is the single riskiest technology in the stack for a no-feedback automated build: cache-invalidation bugs can serve stale builds or effectively brick the origin until a manual unregister, and the update-prompt UX is additional surface that never touches the fun loop. Widest dependency footprint, and two of the five deps solve problems this single-scene game barely has (BVH for a dozen click-time raycast targets; troika for one head-on monitor quad a canvas texture serves). Cold load — the metric actually gated — is unchanged by the PWA.
**Objective alignment:** Strong on durability, observability, and presentation execution; but it spends automated-pipeline reliability (SW complexity) on conveniences the objective doesn't gate, and dependency sprawl dilutes the auditable-privacy story that makes fence 4 cheap to keep.

### Combination 3 — 1A/2B/3C/4B/5C/6C
**"The Diegetic Stage with Engine Wreckage."** Vanilla Three.js at a public static URL — but the code is organized as the facility itself: one Journey-style actor class per station owning its meshes/sounds/animation, a central Director running the locked Visit/Pitch-Cycle statecharts, Rapier WASM in a Web Worker owning the physical aftermath (net interaction, floor settling, ten resting balls), swing judgment kept main-thread and analytic, and an event-sourced save ledger whose projections rebuild every stat from truth.
**Pros:** Code mirrors the locked diegetic UX one-to-one — the fastest structure to navigate for a fixed-cast single scene, and the dominant documented pattern for this stack. Rapier derisks the two signature visual beats most likely to embarrass a hand-rolled solver (believable net reaction, balls accumulating at rest), and the worker hard-isolates their cost from the non-negotiable 60 fps gate. The event ledger makes the honest-stat-board promise true by construction and pre-builds the deferred replay/streak features. Judgment stays analytic on the main thread, so the timing-skill core never crosses a thread boundary.
**Cons:** Gameplay logic distributed across actors plus a worker boundary is the hardest of the three to test headless — yet the locked acceptance scenarios and mastery metrics (median |ε| trends) demand provable timing/scoring math, and determinism must now be policed across an engine the project doesn't own. The ~1.5–2 MB WASM payload nibbles the load gate; the worker message schema is a second serialization boundary; Rapier version pinning is supply-chain surface inside a "local and private" product. Event sourcing is the most code for the same persisted facts, and projection bugs become save bugs. It is heavy machinery for v1's actual physics need: one live ball, a flat floor (damped sphere-on-plane settle), and one-way ball→cloth coupling.
**Objective alignment:** Strongest insurance on two presentation beats; weakest on the deterministic, testable mastery loop the objective scores first — and it pays payload against the time-to-fun gate to buy physics robustness the v1 scene doesn't strictly require.

## Final recommendation
**Rationale:** Combination 1 (1A/2B/3A/4A/5B/6A) as the spine — it is the only combination that simultaneously satisfies the guidance's explicit tech direction, the Slow Roads market positioning the Why is built on, the ≤10 s / ≤60 s time-to-fun gates, and the headless provability that an automated no-feedback pipeline needs to verify its own acceptance criteria. Babylon (1B) and Unity/Godot (1C) are recorded as considered-and-rejected: 1C's documented payloads and lowest-fidelity web renderers directly threaten two non-negotiable gates, and 1B trades the showcase identity for conveniences (engine GUI/audio) the diegetic design never uses. Three surgical grafts repair Combination 1's identified weaknesses without importing Combination 2's risk: (1) from 6B, pmndrs `postprocessing` is admitted as the second and final runtime dependency — the post chain is the one subsystem where bespoke code threatens the *quality* of a hard presentation gate, and a merged-pass production chain is cheaper and faster than the examples EffectComposer it replaces; (2) from 6B, the dev-time tooling comes whole — Playwright automating the three locked acceptance parameterizations, and lil-gui (three's bundled examples module, dev-flag-only, stripped from production) replacing tweakpane so the runtime dep count stays at two — operationalizing the playtest-tuning loop the objective demands at zero runtime cost; (3) from 2C, the PWA is explicitly recorded as a post-v1 fast-follow, keeping the service worker — the riskiest tech for an unattended build — out of v1 while documenting the fence-5-compatible upgrade path. One rule is absorbed from Combination 3's data model motivation: a single-derivation rule (every derived stat recomputed from records in the round-end transaction, never incrementally mutated in a second place) buys 5C's honest-board property without ledger machinery. Finally, 3A is made concrete with the timing decisions downstream milestones hang on: 120 Hz fixed tick, analytic sub-tick ε judgment (so neither frame rate nor tick rate quantizes timing — the locked "frame-rate independent" property becomes provable), cloth as visual-only 60 Hz presentation physics, and no Web Worker in v1. The rejected combinations' remaining deltas (BVH, troika, idb-keyval, Rapier, event sourcing) are individually answered in the components below.

**Final How components:**
- **Language(s) / stack:** TypeScript 5.x (strict) + vanilla Three.js (pinned minor release) + Vite; no UI framework, no react-three-fiber. Rendering baseline: WebGLRenderer on WebGL2 — the shipped, QA'd path for all evergreen desktop browsers; Three's WebGPURenderer behind an experimental `?webgpu=1` flag (same scene graph; post via three's native TSL pipeline there), promoted only when it passes the same visual QA — the honest reading of the locked "WebGL2 baseline, WebGPU optional." Post-processing on the baseline via pmndrs `postprocessing`: merged-pass chain with ACES filmic tonemapping, selective bloom (LED board, release light), and SMAA at the High preset. Diegetic UI rendered in-scene: the LED board and stats monitor are canvas-textured surfaces (custom dot-matrix shader styling for the board, DSEG segment font atlas); machine panel uses emissive PBR materials; only the splash and ESC system sheet are plain HTML/CSS overlays. All gameplay math — fixed-timestep ballistics (gravity + drag; + Magnus post-contact), signed-ε contact model and per-tier window tables, open-field projection-to-ground, Verlet cloth solver, scoring/medals/progression — lives in dependency-free pure-TS modules, headless-testable under Vitest in Node. Audio: Web Audio API directly (no Howler) — one AudioContext unlocked by the splash click, samples decoded to buffers, three's AudioListener/PositionalAudio panners for spatialized sources (machine whirr, plate crack/ping, net rustle), sample-accurate scheduling for the cue set. Asset pipeline: Mixamo → Blender → glTF/GLB; meshopt compression for the animated batter, Draco for static cage geometry, KTX2/Basis textures (UASTC normals, ETC1S albedo); all decoder WASM vendored same-origin. Toolchain gates: tsc strict, ESLint (including an import-boundary rule enforcing core purity) + Prettier, Vitest for core, Playwright (dev-only) for the three locked acceptance scenarios, lil-gui behind a dev flag for live threshold tuning (excluded from production builds). Output is pure static files; no backend of any kind.
- **Deployment & access:** Self-contained static artifact + free static hosting at a stable public URL — the Slow Roads model and the literal fulfillment of the locked "one URL and one key away." `vite build` with a relative base emits one host-agnostic `dist/`: every model, texture, audio file, font, and decoder WASM vendored; zero third-party origins; zero runtime network I/O beyond same-origin static asset fetches at load (the locked "nothing ever touches the network" applies to runtime data egress — nothing is ever sent, and after load nothing is fetched). - **Architecture:** Deterministic headless sim core + presentation adapters (hexagonal, single-threaded), with one-way data flow: platform input adapter → core event queue → fixed-tick sim → snapshots + domain events → presentation and persistence; nothing flows back upstream. `core/` (zero Three.js/DOM imports) owns the entire rules-of-the-game: the Visit and Pitch Cycle statecharts (the locked ARMED→FEED→RELEASE→FLIGHT→INPUT→OUTCOME→RESOLUTION→BOARD_REVEAL sequence), machine feed cadence, the analytic pitch schedule (per-tier release → plate-crossing times), per-speed ε-window tables and the signed-ε contact model, ballistic integrators (pitch: gravity + drag; post-contact: + Magnus; open-field projection integrated to ground for the board's number), an analytic ball-vs-net/cage/floor gameplay response (damped catch on the net, sphere-on-plane settle with sleep, simple sphere-sphere nudges among settled balls), scoring/medals/progression, and stats aggregation — all advancing on a 120 Hz fixed-dt accumulator (Gaffer pattern) fed from a timestamped input queue, emitting immutable per-tick snapshots plus discrete domain events (FEED, RELEASE, SWING_JUDGED{ε, grade, spray}, CONTACT{EV, LA, carry}, NET_HIT, ROUND_END, UNLOCK). Swing judgment is analytic and sub-tick: ε = input timestamp (performance.now() at DOM event time) minus the scheduled plate-crossing time, computed against the continuous schedule — neither frame rate nor tick rate quantizes timing, making the locked frame-rate-independence provable and input-to-judgment latency F3-observable. `presentation/` (Three.js scene graph, camera director with station moves, batter animation controller, LED-board/stats-monitor canvas renderers, audio mixer) subscribes to events and renders snapshot N-1→N interpolated by the accumulator alpha; the Verlet cloth net lives here as visual-only physics (fixed 60 Hz with 2 substeps, one-way coupled — the ball drives the cloth; gameplay outcomes never read cloth state), preserving core determinism. `platform/` adapters: keyboard/mouse input, versioned-JSON save service, clock, seedable RNG, F3 diagnostics. Because core is deterministic and seedable, ε tables, EV/LA formulas, projection math, scoring/medal thresholds, and all three locked acceptance parameterizations run as headless Vitest suites with scripted keypress timestamps. No Web Worker in v1 — one live ball plus visual cloth fits the frame budget and keeps the judgment path boundary-free; re-evaluate only if High-preset profiling shows cloth pressure.
- **Code organization:** Layered tree mirroring the architecture one-to-one (Option 4A), with 4B's actor cohesion preserved inside the presentation layer: `src/main.ts` (splash, audio unlock, boots App) · `app/` (App.ts composition root; GameLoop.ts — rAF + 120 Hz fixed-step accumulator + interpolation alpha; Quality.ts presets + first-run auto-detect; Diagnostics.ts F3 data; events.ts typed bus) · `core/` — PURE TS: pitchCycle.ts (the locked state machine), physics/{ballistics.ts, projection.ts, cloth.ts, collision.ts}, contact/{timingWindows.ts, contactModel.ts}, rules/{round.ts, scoring.ts, progression.ts, stats.ts}, constants.ts (cage dimensions, tiers, physics constants), types.ts, rng.ts · `input/` (swing.ts — SPACE keydown at event time, debounce, lockout, TAKE; uiKeys.ts — arrows/ENTER/TAB/ESC/M/H/B/F3; pointer.ts — raycast click parity) · `scene/` — three.js only: CageScene.ts, CameraRig.ts (OTS + station moves), Lighting.ts, PostFX.ts (ACES, bloom, SMAA), actors/ with one class per station owning meshes/clips/cues but zero rules logic (Batter.ts, Machine.ts, Ball.ts + settled pool, Net.ts cloth-mesh binding, BatRack.ts, TokenSlot.ts) · `ui/` (diegetic/{LedBoard.ts + boardPages/, MachinePanel.ts, StatsMonitor.ts}, overlay/{EscSheet.ts, Splash.ts, KeyHints.ts, Toasts.ts}) · `audio/` (AudioEngine.ts, cueMap.ts event→sample) · `persist/` (schema.ts versioned, store.ts + visibilitychange flush, migrate.ts, exportImport.ts, clipboard.ts) · `assets/` (manifest.ts, loaders.ts) · `tests/` — Vitest suites over core/ (ε tables, EV/LA mapping, projection vs analytic checks, scoring/medal thresholds, state-machine transitions) plus tests/acceptance/ Playwright specs for First Contact, Mastery Session, and Pass-the-Keyboard Duel · `public/assets/`, index.html, vite.config.ts, tsconfig.json. Dependency rule enforced by ESLint import boundaries: core/ imports nothing outside core/; scene/, ui/, audio/ import core types, never the reverse; only persist/ touches storage APIs.
- **Data model:** Hardened single-document save (Option 5B) with a single-derivation rule absorbed from 5C. One versioned localStorage document `bc.save`: meta{schemaVersion, createdAt, updatedAt}; settings{qualityPreset, volumes, mute}; loadout{handedness, bat, lastInitials}; tiers — map keyed "40"…"90", each {unlocked, medals{bronze…platinum}, pbs{bestRoundScore, longestCarryFt, hardestEvMph}, top5:[{initials, score, dateISO}], lifetimeAverages, distanceClubs}; sessions:[{dateISO, rounds, bestScore, medianAbsEpsMs, contactPct, hardHitPct}] kept forever; swingLog FIFO-capped at 10,000 as fixed-order compact tuples [t, tierIdx, epsMs, gradeEnum, sprayEnum, evMphX10, laDeg, carryFt, points, batEnum] (≲0.6 MB at cap); recentRounds referencing swing-log index ranges rather than copying cells. Single-derivation rule: all derived stats (averages, hard-hit %, last-50 sparkline, distance clubs) are recomputed from the round's swing records plus persisted session aggregates in one round-end transaction — never incrementally mutated in a second place — so the board can never show a number the log doesn't support. Durability: every save is double-buffered verify-then-promote (serialize → `bc.save.next` → re-parse to verify → promote, retaining `bc.save.bak`); navigator.storage.persist() requested at first save; writes only at round end and on visibilitychange/beforeunload (synchronous localStorage — never during the Pitch Cycle). Import: hand-rolled runtime schema guards (no validation dependency) → linear vN→vN+1 migration chain; saves from a newer schemaVersion refused with a board message. Export: pretty-printed .json download of the same document; a gentle ESC-sheet toast suggests exporting after a new all-time PB. Worst-case footprint stays well under the 5 MB origin quota with headroom for future fields.
